From 376 seconds to 30.0

How we made colibri's Qwen engine answer a 514-token prompt 13× sooner without changing a single output bit. This is the story from the first measurement to the last check, what changed inside the engine, and what it means for GLM-5.3-Flash.

1
The setting

A model bigger than the machine

colibri runs Mixture-of-Experts (MoE) models on ordinary computers. Each layer of an MoE model holds many small feed-forward networks, the experts. A small router picks a few of them for each token. Only those few run, so the model can be huge while each token stays cheap. colibri keeps a fixed number of experts per layer in RAM (the cap) and reads any other expert from the SSD the moment the router asks for it.

The model

Qwen3-Coder-30B-A3B on colibri's qwen36 engine: 48 layers × 128 experts, 8 chosen per token. Each expert is 2.53 MiB of 4-bit weights, 15.2 GiB of experts in all (19 GB on disk).

The machine

i9-14900HX laptop, NVMe SSD, Windows 11 with WSL2 limited to 12 GB of the 16 GB. The experts cannot all be in RAM, so we test cap 32 (peak 6.3 GB) and cap 12 (peak 3.9 GB, a small machine).

The real target is GLM-5.3-Flash, a 321-billion-parameter MoE whose container is 195 GB. It does not fit here. Qwen3-Coder has the same structure (routed experts streamed from disk through a per-layer cache) and does fit, so it is the stand-in where every idea is measured before it is ported.

Every number on this page comes from cold runs: a fresh process, with the operating system's file cache emptied first, so each expert really comes from the SSD. Variants run back to back in alternating order (A B B A), 3 repetitions each. A change counts only when its bootstrap 95% confidence interval excludes zero; otherwise it is marked n.s.

2
Measuring the original

The time goes to loading, not computing

We first measured the untouched engine on three prompts (24, 161 and 514 tokens) at both caps. Two things stood out.

  • Generating a token is mostly waiting for experts. Fetching experts took 85–94% of every decode step. Each missing expert was read on its own, one after another, while the SSD sat mostly idle.
  • Reading a prompt re-reads the same experts again and again. A prompt of S tokens needs S × 8 experts per layer. When that is more than the cap, the engine falls back to processing one token at a time, and each token evicts experts that later tokens need again. The 514-token prompt read 116,777 experts (283 GB) at cap 12, for a model that has only 6,144 experts in total. Its first token took 483 s.

First change · COLI_Q36_MISS_QD=8

Read a layer's missing experts together

When a layer needs experts that are not cached, the engine now first makes every hit/miss decision in one pass, the exact decisions the original makes in the same order, and then reads the misses 8 at a time. Which experts run, and which get evicted, is unchanged. Only the waiting overlaps.

An investigation · COLI_Q36_FAULT_PROF=1

The page faults were a red herring

Each cache miss still cost about twice what the disk needs. The process took ~3.0 million minor page faults per short run (the operating system mapping a fresh 4 KiB page the first time it is touched), so faults looked like the culprit. We timed every step of a miss and counted its faults:

Where the faults are

phaseminor faults
model load2,025,231
prompt: first touch of the expert cache (48 × 32 slots × 648 pages)995,289

Where a miss really spends time

  • Weight read, 2.36 MB: 8.9 ms
  • A second read for the expert's scales, which the file stores apart from its weights: 2.0 ms
  • Rewriting an evicted cache slot: 3.0 ms, against 0.28 ms for fresh memory, with no fault at all

The slow rewrite comes from outside the program. We read the Windows host's view of the virtual machine during one run:

What this means. The host ran out of memory (4 MB free) and paged most of the VM out, keeping 876 MB of it in RAM while the engine held 4,157 MB. The least recently used cache slot is exactly the memory the host had pushed out, so rewriting it waits for the host. The guest cannot see that wait. The fix is in the environment (give WSL less RAM than the host can back), not in the engine.

A huge-page memory arena (COLI_Q36_SLOT_ARENA=1) removes the first-touch faults (-11% to -34%), but 17 of 18 timing comparisons were not significant. It stays off.

5
Second change · COLI_Q36_PREFILL_WAVES=1

Waves: read each expert once per prompt

The bigger loss was the prompt re-reading experts. Waves turn the loop inside out. Instead of walking token by token, the engine walks expert by expert:

  1. The router runs for every token in the prompt first.
  2. The distinct experts are grouped into waves no larger than the cache. Experts already in RAM go first, so nothing cached is evicted before its turn.
  3. While a wave is in RAM, every token routed to those experts is computed. Each result lands in its own (token, expert) slot.
  4. At the end, each token adds up its 8 results in the original order with the original weights.

Why the output does not change by a single bit. In colibri's expert kernel a token's result from one expert depends only on that token and that expert. Computing it in a different batch gives the same bits, and the final sum is the same statement in the same order as the original. So the model's output is identical, not merely close.

Proof

Same model, same answers

  • Every run wrote the model's final scores over the whole vocabulary (the logits) to a file. We compared their SHA-256 and the generated text with the frozen original binary: 172 runs of the modified engine, 0 differences, across every variant, prompt and cache size, with every flag off and on. The short prompt at cap 32 gives 0306e8f2207cbc0a… every time.
  • Unit tests run real expert kernels on synthetic experts. They check that waves are bit-identical to token-at-a-time, that every (token, expert) pair is computed exactly once, and that no expert is read twice in a layer.
  • Cache decisions are deterministic: hit and miss counts are identical across the repetitions of each variant.

What changed in the engine

All changes are environment flags that are off by default. With every flag off, the engine is the original, bit for bit.

8
The real target

Will it help GLM-5.3-Flash?

We read GLM-5.3's engine (c/glm53.c) before writing any code, so the design could be ported. It already does part of the job:

Already there

  • A layer's missing experts are read in parallel.
  • Prompt processing is already expert by expert, but only inside a 128-token window (GLM53_PREFILL_CHUNK).
  • Experts are read straight into their cache slot, with no repacking.

What would carry over

  • Cached experts first. Today a window's experts go in first-seen order, so an expert already in RAM can be evicted before its turn.
  • A larger planning window. 128 tokens means an expert used across a long prompt is re-read in every window.
  • A fixed-order sum. GLM-5.3 adds expert results in processing order, so reordering would shift the last bits; per-(token, expert) results summed in a fixed order keep it exact.
  • Last-use order, so the answer starts with the right experts cached.
Estimate, not a measurement

On Qwen with waves, planning 128 tokens at a time read 1.8× (cap 32) and 1.8× (cap 12) the bytes of planning the whole 514-token prompt. If GLM-5.3 behaves the same way, a larger window would cut its prompt-time expert reads by roughly 44–45% on ~500-token prompts, more on longer ones, and not at all on prompts under 128 tokens. Cached-first ordering helps most when consecutive windows or requests share experts.

This must be measured on the cloud instance. GLM-5.3 has different expert counts and sizes, different routing and a different memory budget; none of these numbers transfer automatically.

9
Honest limits

What isn't proven yet

  • Decode speed. Three repetitions cannot resolve it under this host's noise. One waves cell measured −28% (medium prompt, cap 32) with first-seen order. The last-use order that is now the default makes its decode cache identical to the original's (2,532 → 1,870 misses), but its own timing test was mixed.
  • The machine. The host was short of memory in nearly every run, so absolute times drift between sessions. Only back-to-back comparisons are claimed.
  • Not measured. Server (warm) mode, colibri's predictive prefetch (PILOT) together with waves, and the GPU paths, which keep the original code.
  • Cold start. 26 of 176 runs began with up to 4.3 MB of the model still cached (the rule is exactly 0), about one expert's worth.

Next steps

Port to GLM-5.3: cached-first waves, the fixed-order sum and a larger window in glm53.c, then measure on the cloud instance with the same cold, alternating protocol and the same bit-exact check.
Re-measure decode on a host with spare RAM, with 6 or more repetitions.
One disk read per expert: merge or overlap the scale read with the weight read.
Decide on defaults: whether waves should be on by default (today it is off, as the project's rules require).
